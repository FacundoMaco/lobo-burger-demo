<objective>
Cerrar PAY-02, PAY-03 y PAY-04: el webhook de Culqi como segundo camino, independiente del
navegador, para que un pago confirmado siempre termine en un pedido registrado.

Hoy el unico camino que escribe una fila en `pedidos` es el navegador llamando a
`POST /api/charge` despues de que el widget de Culqi resuelve el token
(`lib/culqi.ts:196-207`). Si la pestana se cierra, la red se corta, o el celular se
duerme entre la tokenizacion y la respuesta de `/api/charge`, Culqi tiene un cargo exitoso
y no hay pedido — y ningun proceso del lado servidor se entera nunca.

Este plan reemplaza el endpoint temporal de captura que dejo el plan 01-02 por el handler
definitivo, usando el payload real que ese plan documento en `01-CULQI-FLUJO.md`.

Los tres principios de diseno vienen de CONTEXT.md y no se negocian:
  - **D-08:** el payload es un puntero, no un hecho. Se extrae el id y se re-consulta a Culqi.
  - **D-09:** el webhook garantiza que la fila exista; no es dueno del estado del pedido.
  - **D-10:** cero logica basada en los tiempos de reintento de Culqi, que no estan documentados.

Output: `lib/culqi-verificar.ts`, el handler definitivo, y su suite de tests.

**Punto de despliegue seguro — CONDICIONAL, depende de la Task 2:**

- **Si la Task 2 elige la opcion A:** el handler vive en una ruta nueva que hoy solo tiene un
  endpoint de captura temporal. No modifica `app/api/charge/route.ts` ni ningun camino que hoy
  cobra. Riesgo bajo: el peor caso es que el webhook cree pedidos duplicados, mitigado por la
  constraint unica que ya existe en la base y por los tests de carrera de este plan.
- **Si la Task 2 elige la opcion C:** este plan PASA A MODIFICAR `app/api/charge/route.ts`,
  que es el camino que cobra plata real. El riesgo deja de ser bajo. En ese caso la Task 2
  tiene que actualizar `files_modified` en el frontmatter y volver a declarar el riesgo de
  despliegue ANTES de que arranque la Task 3. La red de seguridad es la caracterizacion del
  plan 01-01, que ya cubre el handler.

No dar por buena la version optimista de este parrafo sin haber leido el resultado de la Task 2.
</objective>

**ENTRADA OBLIGATORIA — `01-CULQI-FLUJO.md`** (producido por el plan 01-02). Ese documento
dice cual de los dos flujos de Culqi esta vivo y como se ve el payload real. Sin leerlo,

Los dos flujos posibles y por que importan (RESEARCH.md §Pattern 1, PITFALLS.md pitfall 1):
- **Token sincrono (Cargos Unicos):** id con prefijo `chr_`, evento `charge.succeeded`,
  se consulta con `GET /v2/charges/{id}`. La columna `culqi_charge_id` que ya existe sirve tal cual.
- **Orden asincrona (Ordenes de Pago):** id con prefijo `ord_`, evento `order.status.changed`,
  otro endpoint de consulta. Requeriria una columna `culqi_order_id` nueva y una migracion.
Elegir mal significa que el webhook no recibe nunca el evento que espera.

De `app/api/charge/route.ts:116-148` — el patron de upsert idempotente que hay que REUSAR,
no reinventar:
- `.from("pedidos").insert({...}).select("codigo").single()`
- Si `error.code === "23505"` (unique_violation), se lee la fila existente con
  `.from("pedidos").select("codigo").eq("culqi_charge_id", id).single()` y se devuelve esa.
- Cualquier otro error se loguea y — en el caso de `/api/charge` — no es fatal porque el
  cobro ya ocurrio. En el webhook la postura es distinta: ver D-10 abajo.

De `supabase/migrations/20260820000000_pedidos.sql:5`:
- `culqi_charge_id text not null unique` — esta constraint es el ancla de toda la idempotencia.
  Es lo que hace que la carrera entre el webhook y `/api/charge` sea segura a nivel de base.

Columnas de `pedidos` que el insert necesita: `culqi_charge_id`, `codigo`, `cliente_nombre`,
`cliente_telefono`, `cliente_email`, `delivery`, `direccion`, `lat`, `lng`, `items`,
`total_centimos`. El webhook NO tiene la mayoria de estos datos — solo lo que Culqi devuelve
sobre el cargo. Esto es un problema de diseno real que la Task 2 tiene que resolver
explicitamente, no improvisar.

De `proxy.ts:36-38` (D-11):
- `export const config = { matcher: ["/admin/:path*", "/api/admin/:path*"] }`
- El webhook queda FUERA del matcher. Culqi no puede autenticarse como un navegador; si Basic
  Auth cubriera la ruta, Culqi recibiria 401 y el webhook fallaria en silencio para siempre.

De RESEARCH.md §Code Examples — `extraerChargeId(body)` de referencia: prueba `body.id`,
`body.data.id`, `body.object.id`, y devuelve `null` si ninguna aplica. Falla cerrado.

De `lib/alertas.ts` (plan 01-03): `alertaTelegram(mensaje: string): Promise<void>`, best-effort,
nunca rompe el flujo que la llamo.

De `app/api/charge/route.ts:28-30`: `codigoPedido()` genera `LB-${Date.now().toString(36).toUpperCase()}`.
El webhook necesita generar un codigo cuando crea una fila. Reusar esta misma funcion —
extraerla a un modulo compartido si hace falta, pero NO duplicar la logica.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| internet -> `POST /api/culqi/webhook` | Endpoint publico sin auth y sin firma verificable: cualquiera que descubra la URL puede POSTear |
| webhook -> api.culqi.com | La unica fuente de verdad sobre si un cargo existe y por cuanto |
| webhook -> Supabase `pedidos` | Segundo escritor concurrente sobre una tabla que `/api/charge` tambien escribe |
| `proxy.ts` -> rutas | Si el matcher llegara a cubrir el webhook, Culqi recibiria 401 para siempre |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-33 | Spoofing | Payload `charge.succeeded` fabricado por un tercero para crear un pedido de un cargo que nunca ocurrio | mitigate | D-08: el body es un puntero. Se extrae solo el id y se re-consulta `GET /v2/charges/{id}` con la secret key. Un id inventado devuelve 404 y no se escribe nada. Caso de test 2, obligatorio |
| T-01-34 | Tampering | Monto falsificado en el body para registrar un pedido por un importe distinto al cobrado | mitigate | El monto se toma de la respuesta de Culqi, nunca del body. Caso de test 6 manda un `amount` mentiroso y verifica que se ignora |
| T-01-35 | Tampering | Carrera entre webhook y `/api/charge` creando dos pedidos para el mismo cargo | mitigate | La constraint `culqi_charge_id unique` es el ancla; el handler reusa el catch de `23505` de `app/api/charge/route.ts:134-148`. Casos de test 4 y 5, mas la verificacion en vivo del paso 7 de la Task 4 |
| T-01-36 | Tampering | El webhook pisa campos que `/api/charge` ya escribio con datos mas completos | mitigate | D-09: el webhook garantiza que la fila exista, no es dueno del estado. Caso de test 5 verifica que no se emite ningun `update` |
| T-01-37 | Denial of Service | `proxy.ts` ampliado en el futuro a `/api/:path*` deja el webhook detras de Basic Auth y lo rompe en silencio | mitigate | D-11. `git diff --exit-code -- proxy.ts` es criterio de aceptacion de la Task 3. Vale un comentario en `proxy.ts` advirtiendolo para el futuro |
| T-01-38 | Repudiation | Un evento se pierde porque el handler devolvio 200 ante un fallo real de escritura | mitigate | Caso de test 7: ante un error distinto de `23505` el handler responde no-2xx y alerta. D-10 prohibe razonar sobre reintentos, pero devolver el status correcto es lo que permite que el reintento de Culqi sirva de algo |
| T-01-39 | Information disclosure | `CULQI_SECRET_KEY` filtrada en la URL del GET, en logs o en un mensaje de error | mitigate | Criterio de aceptacion de la Task 1: la clave va solo en el header `Authorization`, nunca concatenada a la URL. El handler no incluye el cuerpo de la respuesta de Culqi en ningun log |
| T-01-40 | Denial of Service | Flood de POSTs al webhook generando una llamada a Culqi por cada uno | accept | Cada POST valido genera un GET a Culqi, que es trabajo real. El rate limiting del plan 01-06 cubre `/api/charge`, no esta ruta. Se acepta para esta fase: el volumen realista de un local de barrio no lo justifica, y `extraerChargeId` descarta el ruido sin salir a la red. Revisar si se observa abuso |
