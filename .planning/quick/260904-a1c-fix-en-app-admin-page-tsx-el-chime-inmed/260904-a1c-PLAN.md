- `app/admin/page.tsx:65` — `playOrderChime()`, funcion de modulo con `globalAudioCtx`

  `pending === 0 || !audioEnabled`.
- `app/admin/page.tsx:401` — chime del pedido simulado.
- `app/admin/page.tsx:1135-1137` — al togglear `audioEnabled` a `true` suena un chime

El interval y el chime inmediato no comparten fase: si `pending > 0` ya estaba corriendo
y entra un pedido, ambos pueden sonar con milisegundos de diferencia.
</current_state>

<chosen_approach>
Gate de espaciado minimo dentro de `playOrderChime` (no re-fasear el interval).

Por que este y no "resetear el interval desde el chime inmediato": resetear obliga a
propagar estado desde el callback de polling (`refresh`, `useCallback([])`) hacia el
efecto del timbre, lo que requiere state nuevo + re-render + reinicio de efecto. El gate
resuelve el sintoma completo (nunca dos sonidos a menos de `CHIME_MIN_GAP_MS`) sin tocar
la estructura de efectos, y ademas cubre el caso simetrico (dos pedidos en el mismo
`refresh`, o simulacion + tick).

`CHIME_MIN_GAP_MS = 1200`: mayor que la cola de 0.5s del chime con margen, y bastante
menor que los 2500ms del interval, asi la persistencia nunca pierde dos ticks seguidos
(peor caso: un tick tragado, repeticion efectiva ≤2.5s).

El toggle "Timbre ON" llama a `reset()` antes de sonar: la confirmacion al usuario nunca
se traga.
</chosen_approach>

<interfaces>
Contrato nuevo (lib/chime-gate.ts), mismo estilo puro que lib/auto-print.ts:

```typescript
export const CHIME_MIN_GAP_MS: number;

export interface ChimeGate {
  shouldPlay(now: number): boolean;
  reset(): void;
}

export function createChimeGate(minGapMs?: number): ChimeGate;
```
