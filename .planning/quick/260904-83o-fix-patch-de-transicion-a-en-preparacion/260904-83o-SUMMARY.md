# Quick Task 260904-83o: Fix patch de transicion a en_preparacion Summary

Cierra el agujero por el que un pedido podia quedar "pendiente para siempre": el PATCH
de `en_preparacion` en `app/admin/page.tsx` era fire-and-forget con `.catch(() => {})`,
asi que un HTTP 500 de Supabase (que `fetch` no rechaza) pasaba como exito silencioso,
la UI mostraba `en_preparacion` optimista, la DB seguia en `pendiente`, y el pedido
nunca volvia a entrar en `incomingOrders`.

## Que se hizo

**Task 1 — `lib/order-transition.ts`:** helper puro (sin `"use client"`, sin DOM, sin
React) que envuelve el PATCH a `/api/admin/pedidos`. Nunca lanza: devuelve
`{ ok: true }`, `{ ok: false, reason: "http_500" }` o `{ ok: false, reason: "network" }`.
Acepta `fetchImpl` inyectable para testear sin mockear el `fetch` global. 4 tests en
`__tests__/order-transition.test.ts` cubren exito, error HTTP, error de red y el body/headers
exactos enviados.

**Task 2 — wiring en `app/admin/page.tsx`:** el callback `onPrinted` de `scheduleAutoPrint`
ahora llama a `persistOrderTransition` en vez del fetch suelto. Ante fallo:
`console.error` con el codigo y la razon, revierte el pedido a `pendiente` en el estado
local, saca el id de `knownOrderIdsRef` (nucleo del fix: habilita que el siguiente poll
de 10s lo vuelva a detectar como entrante y reintente impresion + PATCH), y lo agrega a
un nuevo estado `failedTransitions`. Se agrego un banner rojo en la pestana Pedidos que
lista los codigos afectados y ofrece un boton "Reintentar ahora" que llama a `refresh()`
sin esperar los 10s. `failedTransitions` se purga en cada `refresh()` si la DB confirma
que el pedido ya no esta en `pendiente` (p.ej. via el boton manual "A LA PLANCHA").
